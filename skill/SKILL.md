# 销售客户跟进 → 工作总结

把「我和客户的单聊记录」变成一份能直接发出去的**汇报件**。读者是**直属上级**，不是客户、不是团队知识库。

三个产物分工不同，别混：

| 产物 | 是什么 | 谁看 |
|---|---|---|
| **窗口对话稿** | 切好、分好组、标好方向的原料 | 模型读它抽事项 |
| **事项台账** | 跨期唯一真相，也是**自己的工作日清单** | 销售本人（`next_action` 就是待办） |
| **周期报告** | 台账切出来的汇报件，六种周期都是汇报视图 | 直属上级 |

自己的待办留在台账里，不搬进报告。报告里的每个「下一步」都写成上级能预期的节奏。

## 适用边界

- 只处理**本人视角**：我推进了什么、我承诺了什么、客户卡在哪。
- 只出**本地 Markdown**。要发邮件、进腾讯文档、贴回企微群，都不在本技能里，先出 md 再说。
- **不做**：客户画像打分、赢率预测、收入预测、竞品分析报告。聊天记录不支持这些，硬做就是编。
- **不做**：多人协作的团队周报。多人视角要按人拆台账，不在当前版本内。
- 群聊只在「这个群就是一个客户项目」时纳入；部门群、通知群、内部闲聊群不要采进来。**客户群里我方同事和客户方混着说话，`prepare_window.py` 会按 `sender_is_external` 分开，分不开时不硬猜**（见第 2 步）。

## 一条硬依赖，先讲清楚

**长周期的输入不是消息，是前一周期的报告 + 台账。**

```
消息 ──▶ 窗口稿 ──▶ 事项台账 ──▶ 日报 ──▶ 周报 ──▶ 月报 ──▶ 季报 ──▶ 半年 ──▶ 年报
                        │                    └──────────┴──────────┘
                        └─────── 台账始终是唯一真相，报告只是它的一个切片 ───────┘
```

日/周读消息；月报读周报 + 台账；季报以上只读月报与台账，**不读原始消息**。所以：

- 没有台账，周报就只能是「这周聊了啥」的流水，月报以上做不出来。
- 周报漏写的事，月报补不回来。周报阶段就要把「没推进但有信号」的客户写进去。

## 四个角色

| 角色 | 用什么 | 说明 |
|---|---|---|
| 采集 | `scripts/capture_chat.py`（随技能携带） | 独占企业微信前台读屏；`--singles` 采客户单聊，`--groups` 采客户群 |
| 切窗口 | `scripts/prepare_window.py` | 确定性工作：过滤、分组、排序、统计、识别「谁欠谁一句回复」 |
| 定性 | 模型（本技能的规则） | 哪条消息算工作项、属于哪个客户、到了哪个阶段、是推进还是卡住 |
| 校验 | `scripts/check_ledger.py` | 台账结构、证据可追溯、金额有出处；退出码非 0 不许交付 |

脚本不做语义判断，模型不做算术。

## 主流程

| 步 | 做什么 | 交接物（没拿到就别进下一步） |
|---|---|---|
| 0 | 定范围 | 客户清单、时间窗、采集仓库路径、输出目录、报告周期 |
| 1 | 采集或复用 | 采集仓库（`manifest.json` + `conversations/<key>/current.jsonl`） |
| 2 | 切窗口 | `window.md`、`window.json`、`window.msgs.jsonl` |
| 3 | 抽事项 | 读 `window.md`，产出事项，每条挂 `record_id` + 原文片段 |
| 4 | 并台账 | `ledger.json` 更新完成 |
| 5 | 台账自检 | `check_ledger.py` 退出码 0；`--suggest` 过一遍派生状态 |
| 6 | 渲染 | 对应周期的 md 落到输出目录 |
| 7 | 交付 | 报告 + 「未验证项」段落 |

### 第 0 步：定范围

一次只问缺的那几项，用户已经说了的不要重复问：

1. **客户清单**：先跑 `--singles` 的名字必须与企微侧栏显示一致（常见形态「英文名(中文名)」）。客户群用 `--groups` 另给一份名单，**群名也是逐字一致**。不知道已采过什么就跑 `prepare_window.py --list` 看仓库里现有的会话清单。
2. **时间窗**：`--since` / `--until` 本地日期闭区间，两端都含。日报就是当天；周报是周一至周日；月报是自然月。
3. **采集仓库**：一个账号一个仓库，绝对路径。销售场景单独开一个，别和别的业务混写。
4. **输出目录**：默认 `~/worklog/out/`，台账默认 `~/worklog/ledger.json`。**台账路径定了就不许换**，换了等于丢掉全部历史。
5. **周期**：本次要哪一份，或一次要一串（周五可以一次出周报 + 本周日报）。

🔴 CHECKPOINT：客户清单、时间窗、台账路径三项缺一不可。台账路径每次换，`carry_forward`（延续）就断了，客户会全部变成「新客户」。

### 第 1 步：采集

单聊是主战场。第一次跑之前先 `--prepare-only` 核对打印出来的 `[single]` 清单：

```bash
python3 scripts/capture_chat.py \
  --store ~/wecom-data/wecom-chat-sales \
  --singles "张三,李四(某科技),王五" \
  --start 2025-11-01 --end 2026-11-25 \
  --account-label sales \
  --self-names "<本人中文名>"
```

三条必须记住的：

- **`--start` 一旦定了就不能改**，同一仓库内固定；以后延长只改 `--end`。所以第一次就把 `--start` 设到你真正想回溯的最早点（至少覆盖一个季度，做年报就要覆盖全年），改不了。
- 客户群用 `--groups` 一起采，名字必须与企微显示一致；改过名的群用当前名字。
- 采集独占前台、模拟滚动，**跑的时候别动那台机器**。手动模式下建议一次采一周，跑完再干活。

采集失败不要原地重试：锁屏/息屏/布局变化属正常中断，恢复后续跑；弹窗阻塞要人工确认后加 `--retry-dialog-blocked`。退出码表见 `references/capture.md`。

已有采集仓库或导出文件时跳过本步。没有采集环境（非 macOS、没授权）就用导出的 JSONL，必需字段见 `references/capture.md`。

### 第 2 步：切窗口

```bash
# 日报：直接给日期
python3 scripts/prepare_window.py \
  --store ~/wecom-data/wecom-chat-sales \
  --since 2026-11-25 --until 2026-11-25 \
  --out ~/worklog/runs/2026-11-25 \
  --self-names "<本人中文名>,<本人账号>" \
  --silence-days 7 --awaiting-days 2

# 周报 / 月报：用 --week / --month，别手写日期（跨月、跨年、记错周几都会错）
python3 scripts/prepare_window.py --store <仓库> --week 2026-W48 --out <目录>
python3 scripts/prepare_window.py --store <仓库> --month 2026-11 --out <目录>
```

`--week` 按 ISO 周算（周一起、周日止），跟 `2026-W48-weekly.md` 的文件名口径一致；`--month` 是自然月。只写 `--week` / `--month` 不带值时表示本周 / 本月。给了它们就忽略 `--since/--until`（会 warn 一句）。

周期末晚于今天时，「距最后一条」和静默天数按**今天**算，不按周期末——月中跑整月报不会把一个 3 天前刚聊过的客户算成 10 天没动静。`window.json` 的 `window.ref_date` 就是这个基准。

产出三份：

| 文件 | 给谁看 | 内容 |
|---|---|---|
| `window.md` | 模型读这个 | 按客户分组、按天分段的可读对话稿，标了方向、时间、引用 |
| `window.json` | 模型取数字 | 每客户的条数、首末时间、沉默天数、结构信号；全局覆盖声明 |
| `window.msgs.jsonl` | 校验用 | 窗口内原始消息，`check_ledger.py` 拿它核对证据 |

**不要直接读 `current.jsonl`**：字段多、噪声大、token 贵，而且没有分组和排序。窗口稿就是为读而生的。

`window.json` 里的结构信号是纯确定性的，零幻觉，销售最该看：

- `awaiting_me` —— 最后一句是客户说的，已经过了 N 天，**我欠客户一个回复**。
- `awaiting_client` —— 最后一句是我说的，过了 N 天，**客户没回**。
- `silent` —— 整个窗口客户一条没说，只有我在发。
- `side_unknown` / `awaiting_check` —— 群聊里分不清谁是我方谁是客户，**不下结论，挂给人看**。

前三个直接进报告的「风险」段，不需要模型再判断。

### 群聊怎么读

采了客户群时，窗口稿标题下会多一行分边统计：

```
> 群聊分边（群消息 9 条）：我 2 ｜ 我方同事 1 ｜ 客户方 3 ｜ 未标注 3
```

- **`我方同事` 不是客户**。同事在群里说「实施我接，下周一出排期」，是我方内部动作，不能算客户回应，也不能算客户需求确认。
- **`未标注` 不要自己补**。这个数 > 0 说明该群部分成员查不到内外身份；`client_side_known=false` 的群，脚本连 `silent` / `awaiting_*` 都不产出，窗口稿里会有一行警告。这时报告里只能写「该群分边未确认」，不要写「客户在等我们」。
- 引用数字用 `totals.group_sides`（`me` / `ours` / `theirs` / `unknown`），不要用 `totals.their_messages`——那个把同事也算进去了。

先看三件事再往下走：

- **方向**：标题行里的「我 N / 对方 M」。出现 `我 0` 说明方向判定失效（`is_outgoing` 缺失且 `--self-names` 没对上），必须先把名字补对——否则整个窗口看起来是客户独白，报告必然失真。
- **覆盖**：`coverage.incomplete` 是一个**客户名列表**，列进来的客户本窗口都不是完整历史；逐个看它们各自的 `history_complete`，值为 `false`。`coverage.all_complete=true` 表示整个窗口都完整。
- **分边**：有群时看 `coverage.groups_side_unknown`。非 0 就把那几个群单独列进「未验证项」。

🔴 CHECKPOINT：先看 `coverage`。只要 `coverage.incomplete` 非空（等价于这些会话 `history_complete=false`），报告里必须逐个写「该客户本窗口不是完整历史」，不能据此说「本月无进展」。

### 第 3 步：抽事项

读 `window.md`，对每个客户问三个问题：

1. 这次沟通**有没有让事情往前走**？（有 → 更新事项；没有 → 不写）
2. 走到哪一步了？（阶段，见 `references/sales-signals.md`）
3. 我答应了什么、客户答应了什么、下一次触达是什么时候？

**什么算一个事项**：一条能独立讲清楚的客户推进线，例如「某科技-报价与折扣」「某银行-试用环境」。同一个客户的报价和试用是两个事项，不要糊成一条。

**什么不算**（丢弃清单在 `references/sales-signals.md`）：寒暄、节日问候、纯发资料无回应、转发新闻、约时间没约成、系统通知。

每个事项必须挂证据：`record_id`（32 位十六进制）+ `quote` 原文片段。`quote` 的口径决定了报告能不能加引号，写错了第 5 步会被拦回来重做：

| 情况 | 怎么写 |
|---|---|
| 客户原话记得准 | 截取原文**连续片段**，≤60 字，中间省略用 `……` |
| 只记得大意 | 不许加引号，写成转述并标 `（推断）`，该条 `quote` 留空 |
| 完全挂不上证据 | 标 `（推断）` 或直接不写，不建 item |

🔴 CHECKPOINT：这一步有两个硬闸，过不了第 5 步会退出码 1、不许渲染。

- **引号内必须是原文**：`check_ledger.py` 拿 `quote` 去 `window.msgs.jsonl` 里逐字比对，概括、改词、跨消息拼接都会报 `E_QUOTE_NOT_GROUNDED`。
- **金额、日期、数量只能来自原文**：客户说「预算 30 万以内」才能写 30 万；客户没说就写「金额未提及」。不许写「预计签约 50 万」「按 30% 赢率折算」，脚本会去原文里找那个数字，找不到直接报错。

### 第 4 步：并台账

台账是单个 JSON 文件，结构见 `references/ledger.md`。更新规则只有四条：

| 情况 | 动作 |
|---|---|
| 窗口里出现了全新的一条推进线 | 新建 item，`opened_at` = 首次出现的日期 |
| 已有 item 有新进展 | 更新 `stage` / `status` / `last_update_at` / `next_action`，追加一条 `status_history` 与 evidence |
| 已有 item 本周没被提到，也没闭环 | 什么都不改。不要因为它没动静就删或改状态 |
| 客户明确说了不做、选了别家、项目取消 | `status=lost`，必须附客户原话作为 evidence |

`active` 的事项目标是「下次什么时候动它」。`next_action` 为空且 `status=active` 的条目，等于没在管，自检会提示。

### 第 5 步：台账自检（硬闸）

```bash
python3 scripts/check_ledger.py --ledger ~/worklog/ledger.json \
  --window ~/worklog/runs/2026-11-25/window.msgs.jsonl \
  --until 2026-11-25 --suggest
```

**退出码非 0 不许渲染报告。** ERROR 级：结构不合法、`item_id` 重复或格式错、`status`/`stage` 不在枚举内、没有 evidence、金额在原文里找不到、**`quote` 在原文里找不到**、`status_history` 时间倒流、`done`/`lost` 缺证据、正文里有手机号/邮箱/证件号。

`--suggest` 只输出建议不改文件，派生状态由脚本算，不靠模型记忆。左列就是脚本原样打印的代码，排查时照抄：

| 代码 | 含义 | 去哪 |
|---|---|---|
| `S_STALLED` | `last_update_at` 距 `--until` 超过 `silence-days` | 周报「风险与卡点」 |
| `S_OVERDUE` | `next_action_due` 已过期且 `status=active` | 日报「明日动作」第一行 |
| `S_VANISHED` | 超过 2 倍 `silence-days` 没有证据追加 —— 人工确认是丢了还是搁置了 | 月报「客户结构」 |
| `S_STALE_PROMISE` | 最后一条证据是我方承诺，之后没有我方消息 | 周报「我方承诺未闭环」 |
| `S_REGRESSED` | 阶段序号下降（如 `negotiation → quote`） | 风险段**第一行**，比停滞更紧急 |
| `S_REVIVED` | 沉默超 2 倍阈值后重新有往来 | 「本周推进」并标「复活」 |

前四个告诉你「没动静」，后两个告诉你「动了但方向不对」和「动了但差点被放弃」。**销售最贵的预警是后两个**：客户没消失，只是退回去了。

WARN 逐条看，不必全改：title 超过 40 字、`next_action` 为空、evidence 的 quote 超过 60 字、金额缺 `source`。

### 第 6 步：渲染

六种周期的骨架、问句、篇幅、数据来源都在 `references/renderers.md`。这里只讲不变的规矩：

- **六种报告都是给 leader 的汇报件，不是自己的工作记录。** 自己的待办留在台账里；报告里的「下一步」写成 leader 能预期的节奏。
- **先读台账，再读窗口稿**。日报/周报可以读窗口稿补充细节；月报以上只读台账与上期报告，不碰原始消息。
- 数字只从 `window.json` 或台账来，不自己数。
- 每条结论后面挂时间锚 `（11-25 15:10）` 或 `（推断）`；月报以上只给金额和反直觉结论挂锚，其余进「证据索引」。
- 报告里不出现「大概」「预计」「有望」+ 数字的组合，除非那是客户原话的转述。
- 周报以上必须有 `## 需要你拍板` 一节，**每项给两个选项**加期限；没有就写「无」。
- 客户原话按配额取（日 1 / 周 2 / 月 3 / 季 5 / 年 8），只从台账 `quote` 取，引号内即原文。
- **开头一行元信息**：标题下一行写窗口 / 台账版本 / 覆盖 / 生成时间，格式见 `renderers.md` 第 0 节。归档后靠这一行分清哪份报告基于哪版数据。
- 输出文件名固定：`2026-11-25-daily.md`、`2026-W48-weekly.md`、`2026-11-monthly.md`、`2026-Q4-quarterly.md`、`2026-H2-halfyear.md`、`2026-annual.md`。

**交付前三步验收**（不过就重写）：

1. **标题串测试**：把全文所有 `###` 抽出来连读，应该是一段读得通的话。
2. **决定测试**：leader 读完能不能回答「我要不要做决定、做什么决定」。
3. **删段测试**：删掉任意一段，报告是否变弱。不变弱的那段是水。

月报以上需要「基准」。用户给了本月目标就写完成度；没给就写「本期未提供目标，以下只报进展」，**不许自己造一个百分比**。

### 第 7 步：交付

报告末尾固定两段：

```markdown
## 数据与覆盖
- 窗口：2026-11-19 ~ 2026-11-25 ｜ 客户 7 个 ｜ 消息 214 条（我 96 / 客户 118）
- 采集覆盖：history_complete 6/7；「王五」本窗口不是完整历史
- 未跟进：本周有沟通但零推进的客户 3 个（张三、李四、赵六）

## 未验证项
- 客户口头承诺未落合同的部分，只记录不代表已确认
- 竞品信息仅转述客户原话，未核实
```

没采全就说没采全，没确认就说没确认。**报告的可信度来自它承认了什么，不是它写了多少。**

## 硬限制

1. **不编数字**：金额、数量、日期只能来自原文；找不到出处就不写。
2. **不编因果**：客户没回 ≠ 客户不满意；写「已 12 天未回」，不写「客户可能已放弃」。
3. **不跳过台账**：直接拿聊天记录写周报，等于每周重新发明一遍历史，客户会重复出现、状态会前后矛盾。
4. **不改历史条目**：`closed_at`、`opened_at`、既有 `status_history` 只追加不覆盖。
5. **不把客户名当敏感信息删掉**：这份总结是给你自己和上级看的，客户名是主键，删了看不懂。要对外发送时用 `--redact all` 换成代号。
6. **不写手机号/邮箱/证件号/银行账号**：这些进 md 就是泄漏，一律打码。
7. **不承诺能力**：`awaiting_client` 只说明「客户没回」，不代表商机死了；报告里按事实写，不给结论式判决。
8. **不并行跑两次**：台账是单文件，后写覆盖前写。
9. **不编原话**：引号内必须是台账的 `quote`，而 `quote` 必须是原文片段（脚本会核对）。说不出原话就改成不加引号的转述并标 `（推断）`。
10. **不交「只描述、不请示」的报告**：周报以上是汇报件，`需要你拍板` 要么有内容，要么明确写「无」。写给 leader 却没有一句话需要他做决定，这份报告就白写了。

## 排查顺序

| 现象 | 一线修复 | 仍不行 |
|---|---|---|
| `prepare_window.py` 报 0 个会话 | 核对 `--singles` 名字与侧栏是否逐字一致；`--groups` 也会过滤，别混填 | 仓库里没有该会话 → 先采集；名字改过就用新名字 |
| 窗口内消息比预期少 | `--since/--until` 是闭区间，跨月要注意月份天数 | manifest 里 `latest_message_at` 早于 `--since` → 该客户这段时间确实没聊 |
| 标题行显示「我 0 / 对方 N」 | `is_outgoing` 缺失，且 `--self-names` 没对上。补 `--self-names "温志聪,bennywen"`（中文名与账号都要） | 仍为 0 → 看 `sender_raw` 是什么形态，按它原样填 |
| 群里同事的话被当成客户回应 | 看 `totals.group_sides`，`ours` 是同事发言；`their_messages` 里混了同事，别用 | 该群成员在通讯录里没有内外标记 → 重采并确认通讯录可用 |
| 群里整段都是「未标注」 | `sender_is_external` 全空，脚本按 `side_unknown` 处理、不产出 `silent`/`awaiting_*` | 报告里写「该群分边未确认」，放进未验证项，别自己判 |
| `coverage.groups_side_unknown` 不为 0 | 对应群在窗口稿里有警告行 | 逐个确认是不是「一个群 = 一个客户项目」，不是就从台账排除 |
| 客户名对不上 | 单聊名常是「英文名(中文名)」，按侧栏原文填 | 同名不同公司会出现多个 `conversation_key`，按 key 分开处理，不合并 |
| 采集退出码 20/21/22/23 | 锁屏、息屏、布局变化、焦点丢失，恢复后续跑 | 25 弹窗阻塞 → 人工处理后加 `--retry-dialog-blocked` |
| 台账出现两个同客户同主题的 item | 合并：保留早的 `item_id`，把晚的 evidence 并过去，`status_history` 按时间插入 | 不要删 `item_id` 后重建，历史 evidence 会失联 |
| `check_ledger.py` 报 `amount_not_grounded` | 回原文确认客户到底怎么说的（「30 万」和「30w」都要试） | 原文确实没有 → 删掉 `amount` 字段，改写「金额未提及」 |
| `check_ledger.py` 报 `E_QUOTE_NOT_GROUNDED` | 回窗口稿把那条消息的原文截一段（≤60 字，连续片段）替换掉概括句，省略处用 `……` | 原文里确实没有能支撑该结论的句子 → 删掉 `quote`，把判断改成不加引号的 `（推断）` 转述 |
| 台账报 `W_QUOTE_EMPTY` | 这是预期告警不是错误：说明该条只有转述没有原文，报告里相应位置不能加引号 | 想在报告里加引号 → 必须补回原文片段，补不上就改写成转述 |
| 月报写不出「完成度」 | 因为没目标。问用户要一句本月目标 | 用户不给 → 只报进展，标题写「进展月报」 |
| 周报里某客户消失了 | 查台账该 item 是否 `S_STALLED` / `S_VANISHED` | 消失了但没闭环 → 这本身要写进风险段 |
| 客户从谈合同退回报价，周报里当成了普通推进 | 跑 `--suggest` 看 `S_REGRESSED`，它比对的是 `status_history` 的阶段序号 | 台账记了但 `status_history` 没写阶段变化 → 回窗口稿确认客户到底说了什么，补一条再算 |
| 沉默很久的客户在报告里被当成新客户重新介绍 | 跑 `--suggest` 看 `S_REVIVED`（相邻证据间隔 > 2×`silence-days` 且最近一条在本周期内） | 确实断了很久 → 报告里标「复活」，仍沿用原 `item_id`，不要新建 |

## 质量自查

- [ ] 窗口的客户清单、消息数、覆盖声明都进了交付段
- [ ] `awaiting_me` / `awaiting_client` / `silent` 三类都处理了（写进风险或说明为什么不算风险）
- [ ] 有群时，来自群的结论区分了「我方同事」和「客户方」；`side_unknown` 的群进了未验证项
- [ ] 每条推进都有 `record_id` 证据与时间锚
- [ ] 金额出现的地方，原文都能对上
- [ ] 原话达到配额（日 1 / 周 2 / 月 3 / 季 5 / 年 8），且引号内都能在台账 `quote` 里找到
- [ ] 全文 `###` 抽出来连读读得通，不是一串「客户名 —— 阶段（状态）」标签
- [ ] 周报以上有「需要你拍板」，每项两个选项 + 期限；没有就写了「无」
- [ ] 报告头有一行元信息（窗口 / 台账版本 / 覆盖 / 生成时间）
- [ ] `S_REGRESSED` 的客户排在风险段第一行，`S_REVIVED` 的客户标了「复活」
- [ ] 月报以上有「证据索引」，正文只给金额与反直觉结论挂锚
- [ ] 没有「预计 / 大概 / 有望 + 数字」
- [ ] 台账 `check_ledger.py` 退出码 0
- [ ] 上月/上周已在报告里出现的事项，本期是「延续」不是「重新介绍」
- [ ] `S_STALLED` / `S_OVERDUE` / `S_VANISHED` 的客户在风险段有交代
- [ ] 报告末尾有「未验证项」，没把客户口头承诺写成已确认

## 🛑 停止条件

- 用户要求「不用台账，直接根据这周聊天记录写」→ 拒绝并说明：这样每次都是新的，无法体现延续与卡点。可以退一步：只出「本周沟通摘要」，不叫工作总结。
- 用户要求预测成交金额/赢率/下季度收入 → 拒绝。可提供「客户明确说过的预算与时间点」清单。
- 用户要求把客户名、电话、合同金额全部原样写进要外发的文档 → 提示 `--redact all`，或让用户自己确认外发范围。
- 采集环境不可用且没有导出文件 → 交「窗口无法生成」的说明与所需字段清单，不要凭记忆写报告。
- 台账与窗口证据冲突（台账说已成交，窗口里客户说还在审批）→ 停在冲突处，列两种说法与出处，让人裁决。
