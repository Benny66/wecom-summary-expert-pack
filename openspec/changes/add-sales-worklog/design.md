# 设计：销售客户跟进 → 六种周期报告

## Context

用户是销售，数据是**他和客户的单聊**，交付要**本地 Markdown**，触发方式**手动**。

现有资产是企业微信采集链路：`scripts/wecom/`（13 py + 6 swift）把企微读屏 + 滚动落成 `manifest.json` + `conversations/<key>/current.jsonl`。它原本取的方向字段是 `sender == "我"`，真实数据里自己发的其实是本人中文名 + `is_outgoing=true`，这一点在本设计中已修正（见 D9）。

那条链路原本的语义是「群问答 → 知识库条目」，用不上。可复用的是采集本身、以及「脚本做确定性工作、模型做语义判断、硬闸挡编造」这条方法论。

## Goals / Non-Goals

**Goals**

1. 一个人能每天/每周用几分钟拿到一份自己愿意看的总结，不需要记参数。
2. 六种周期共用**一份事实层**，同一条事项在日、周、月、年里的说法不打架。
3. 每条结论都能点回一条具体消息；金额、日期、数量不能凭空出现。
4. 跨期连续性：上周说「等审批」，这周写「仍未获批（第 2 周）」，而不是重新介绍。

**Non-Goals**

- 不做团队多人视角（那要按人拆台账，另开变更）。
- 不写知识库、不进腾讯文档、不发邮件（本地 md 是第一交付形态）。
- 不预测成交金额、赢率、下季度收入。
- 不做客户画像打分、竞品分析报告。

## Decisions

### D1：工作线 = 客户 × 主题，不是「群」

按会话组织的台账适合检索型知识库；销售场景里**一个客户可能同时有三条线**（报价、另一个产品试用、售后问题），群也不能代表客户（很多客户只走单聊）。

所以台账的 `item` 是「客户 + 一个能独立讲清的主题」，`conversation_key` 只作为来源字段。合并/拆分的判据写在 `references/sales-signals.md` 第 8 节。

代价：模型要做一次「这是新线还是旧线」的判断，不能靠会话 id 自动分组。收益：周报能写出「某科技：报价在谈、试用已开通」这种真实结构。

### D2：六个周期分三组渲染，季报以上不读原始消息

| 组 | 周期 | 问句 | 输入 |
|---|---|---|---|
| 描述 | 日报、周报 | 发生了什么 | 窗口稿 + 台账 |
| 对比 | 月报 | 和计划的差距 | 周报 + 台账（**需要基准**） |
| 评价 | 季报、半年、年报 | 什么变了、什么该停 | 月报 + 台账 |

硬约束：季报以上**只读**月报与台账。理由是容量与注意力双重限制——一年二十万条消息既塞不进上下文，也没法从里面看出主线。副产物是：想写年报，必须先把周报/月报写起来。

月报的「对比」必须有基准。没有月初目标就声明「本期未提供目标，只报进展」，**不许生成完成度百分比**。这是本设计里唯一一处宁可少写也不能多写的地方。

### D3：台账语义从「防重复」改成「叙事连续性」

| 本设计 | 为什么这样 |
|---|---|
| `item_id` + `status_history`（不用内容哈希） | 要回答「这条线几个月了、卡过几次」，内容变没变不是重点 |
| 延续 `carry_forward`（不用「没变化就跳过」） | 上期说「等审批」，本期要写「仍未获批（第 N 周）」 |
| `stalled` / `overdue` / `vanished` 全由脚本算 | 派生状态不靠模型记 |
| 合并时保留早的 `item_id`（不重建） | 合并错了还能靠 evidence 修，重建 id 就断链 |

`vanished`（长期无动静、也没明确死掉）是销售特有的：它既不是 active 也不是 lost，硬塞进任一边都会失真。脚本只提示，人确认。

### D4：同一个配对信号，在两个场景里用法相反

做知识库时，`quote_tail`（引用上一轮答复再追问）是**噪声**——追问不是答案，直接丢弃。

销售场景里「同一个承诺被追问第二次」是**最有价值的风险信号**——说明我方承诺没兑现。`prepare_window.py` 因此不算配对，只算结构信号（`awaiting_me` / `awaiting_client` / `silent`），把语义解释留给模型与台账的 `S_STALE_PROMISE` 建议。

### D5：金额三重闸

1. **规则层**：`amount` 只有 `value` / `currency` / `source` / `evidence_msg_id` 四项，缺一项即 ERROR。禁止「报价 × 赢率」这类派生值。
2. **脚本层**：`check_ledger.py` 把 `value` 展开成 `300000` / `300,000` / `30万` / `30w` / `30k` 等写法，去 evidence 那条消息的原文里找，找不到报 `E_AMOUNT_NOT_GROUNDED` 并退出 1。
3. **渲染层**：原文是「30 万以内」时，报告必须写「预算上限 30 万」，不能写「预算 30 万」。

设计取舍：只看字面匹配会漏掉「三十万」「3 后面 5 个 0」这类写法。选择**宁漏不猜**——漏了只是少写一个数字，猜了就是造假。

### D6：客户名保留，数字打码

写公共知识库的台账必须匿名。销售总结是私人台账，**客户名是主键**，删了看不懂。

所以默认 `--redact pii`：手机号、证件号、银行卡、邮箱打码，人名公司名保留。要外发才用 `--redact all` 换代号，且明确告知「正文里的真名不替换」。

### D7：交付本地 md，手动触发

- 文件名固定（`2026-11-25-daily.md`、`2026-W48-weekly.md`…），方便按目录归档、grep、贴群。
- 不用 MCP：没有服务端依赖，断网也能写完。
- 手动触发是**已知代价**：采集器独占前台，日报想自动化就要在无人时段跑。当前版本不解决，`tasks.md` 里列为后续项（评估企微「会话内容存档」官方通道）。

### D8：群里的「对方」必须拆成我方同事 / 客户方

客户群里我方同事和客户混着说话。只数「我 / 对方」的后果不是少一点精度，而是**结论方向反了**：

- 客户一周没吭声，但同事天天在群里汇报进度 → 读成「客户很活跃、沟通顺畅」
- 同事答应「下周一出排期」→ 读成「客户承诺了时间点」
- 反过来，客户零发言被同事的发言掩盖 → `silent` 不亮，风险段漏掉

所以按 `sender_is_external` 把每条消息分成 `me` / `ours` / `theirs` / `unknown` 四类：

1. **只在 `client_side_known` 时产出结论**。该字段全为 `null`（通讯录没导全）时不产出 `silent` / `awaiting_*`，改打 `side_unknown` + `awaiting_check`，窗口稿里挂警告。宁可漏一条，不编一条。
2. **判「已知」只看对方的消息**。我自己那条通常是 `false`（我当然是内部的），拿它当证据会让整段客户消息都是 `null` 的群被误判成已知。
3. **单聊的非我消息一律规整成客户方**。`sender_is_external` 为 `null` 的单聊若走同一套分类会落到 `unknown`，`awaiting_me` / `awaiting_client` 静默消失——这是最容易漏的一处。
4. **台账不按渠道建 item**。同一客户既有单聊又有群，仍然按「客户 × 主题」建一条线，`channel` 只记来源。群只有「整个群 = 一个客户项目」才纳进来，部门群/通知群/跨客户行业群不进。
5. **`conversation_type` 缺失不默认成单聊**。按「非我的不同发言人是否多于 1 人」兜底；默认成单聊会把群里的同事全算成客户。

代价是窗口稿多了一份分边统计和名册，token 略增；换来的是群里那部分结论不再靠猜。

### D9：方向与顺序按采集器的原始证据判，不按显示名猜

三条只有真实数据才暴露的坑：

1. **方向**：单聊界面不渲染发送者名字，自己发的消息 `sender` 是本人中文名（如「温志聪」），不是「我」。写死 `sender == "我"` 会让整个窗口看起来是客户独白（实测 `我 0 / 对方 20`）。改为**优先 `is_outgoing`**，`--self-names` 只在字段缺失时兜底。
2. **同分钟顺序**：`record_id` 是正文哈希 + 同屏序号，跨屏看是随机的。拿 `(sent_at, record_id)` 排序会把同一分钟的来回对话打乱。改为**只按 `sent_at` 稳定排序**——采集落盘顺序就是气泡的视觉顺序。
3. **群话分边**：见 D8。

共同点：能用采集器的原始证据（`is_outgoing`、落盘顺序）就别用名字或哈希去猜，猜错的时候报告不会报错，只会安静地写反。

## 复用与不复用

| | 内容 | 说明 |
|---|---|---|
| 原样复用 | `scripts/wecom/`、`capture_chat.py`、`check_environment.py` | 采集器整体照搬，只修方向字段与排序口径（D9）；仓库格式不变，已有采集仓库可直接复用 |
| 换语义 | 流水线骨架 | 「过滤 → 分段 → 配对 → 打分」改成「过滤 → 分组 → 统计 → 结构信号」——销售不需要给消息打分，需要知道谁在等谁 |
| 换语义 | 台账 | 见 D3 |
| 借用 | 校验闸门的形态 | error 挡下游 + 退出码；判据换成证据 / 金额 / PII |
| 弃用 | 知识库同步、去重矩阵、MCP 写入 | 没有下游知识库，也没有远端要写 |
| 新写 | 事项抽取（模型）、六种渲染器、周期滚动、群话分边 | 主要工作量 |

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|---|---|---|
| 台账漂移（同一客户被拆成多条线） | 周报看起来商机变多，实际是重复 | 合并规则 + `W_DUP_TITLE` 告警；`item_id` 分配后不改 |
| 长周期缺原料（没写周报就想过年报） | 年报只能写空壳 | 报告里明写「缺 X 期报告」，不许用台账硬撑出叙事 |
| 采集独占前台 | 日报难以每天自动跑 | 手动一次采一周；后续评估官方会话存档 |
| 群聊分边依赖通讯录 | 通讯录没导全时整段群消息落在「未标注」，群里那部分只能写「分边未确认」 | 不硬猜，挂 `side_unknown` 进未验证项；重采并确认通讯录可用可解 |
| 模型把「客户没回」写成「客户不感兴趣」 | 报告失真、误导决策 | 风险口径只写事实；`renderers.md` 明令禁止结论式判决 |
| 金额漏检（三十万 / 中文数字） | 少数金额未被核对 | 宁漏不猜，明确写入 `sales-signals.md` |
| 单聊数据含个人隐私 | 泄漏风险 | 默认 pii 打码；外发走 `--redact all` 并人工复核 |

## Migration

无历史数据迁移。首次使用：装好技能（采集模块随包携带）→ 采集（`--start` 一次性设到最早回溯点）→ 跑一次窗口 → 由模型建立初版台账 → 校验通过后开始出报告。

## Open Questions

1. 周报的「周」以周一还是周日为界？（当前按 ISO 周，周一到周日）
2. 月报基准（月初目标）存哪里：台账顶层字段，还是单独 `goals.json`？（当前倾向台账顶层，少一个文件）
3. 是否需要「客户档案」页（每个客户一页，汇总所有 items 与时间线）？当前版本只有台账与报告。
